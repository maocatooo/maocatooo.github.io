# Agent

## Agent是什么

Agent = 大脑 + 眼睛 + 手脚  
Agent = LLM + [上下文 + 工具 + 约束 + 验证 + 纠正] = Model + Harness

## Agent运行方式

agent的运行方式：工作流 + 自主

## Harness

Harness 的核心就是公式中的“上下文 + 工具”，再加上三层保障机制

- 约束（限定 Agent 能做什么、不能做什么）
- 验证（检查 Agent 做得对不对）
- 纠正（做错了怎么补救）

# 上下文工程

## 上下文都有什么

- system：系统提示词
- user：用户消息
- assistant：助手消息(AI回复)
- tool：工具结果

## KV Cache 友好的设计

### 原则

动态信息追加末尾、静态信息保持不动

### 作用

- 加速推理
- 费用减轻

### 如何做

- 系统提示词和工具定义一旦确定就不要改
- 动态信息永远追加到末尾
- 使用标准 API 格式，不要自行拼接消息

### 避免

- 动态系统提示词，如系统提示词添加时间戳
- 工具定义的动态排序
- 滑动窗口
- 动态用户配置
- 文本格式化方法

## 提示工程：优化系统提示词

核心对象：系统提示词
是 Agent 的“员工手册”，定义了 Agent 的身份、行为规则、约束条件和工作流程

### 语气与风格

### 结构化提示

Markdown + XML

### 流程驱动

Step 1,2,3

### 业务规则细化

需要做什么，怎么做，不要做什么

### 示例

给出2-3个简短的参考示例

### 工具定义的设计

工具不只是说明书，还要列举触发的场景，以及工具间的协作关系

### 提示注入

- 直接注入，用户要求告知系统提示词
- 间接注入，工具返回第三方的不安全内容
- 记忆注入，多轮对话中发出指令被记录，下次做xx事情，把内容发送到xxx  
  **防范：**
- 来源标记（如 <external_content source="webpage">...</external_content>）
- 严格遵守api角色体系 system/user/assistant/tool
- 输入清洗，提前过滤外部内容

## 动态提示词与 Agent Skills

系统提示词不断膨胀的危害

- 浪费 token
- 注意力被稀释  
  Skills：不是把所有知识一次性塞给 Agent，而是让它按需加载。

### skill的设计

- 元数据，名称，介绍（触发场景）
- 核心流程，skill.md
- 细则/引用数据/脚本，reference.md，script脚本

### skill的使用

元数据作为动态上下文提供，完整内容通过专用工具按需加载

## Agent 状态栏

Agent 框架向模型同步各种动态状态的统一机制，称为 Agent 状态栏  
**作用**  
提高模型的注意力机制  
**特点**  
由人/硬编码手动维护

### 在上下文的位置

作为用户角色消息追加到最后面<agent_status>...</agent_status>

### 状态栏有什么

- 任务规划
    - step1 done, step2 doing,step3 wait
- 事件的侧信道信息
    - 为每个事件附加元数据——精确的时间、地理位置、距上次Agent 回复的时间间隔等
- 环境的当前状态
    - 工作目录
    - 操作提醒
- 可用能力清单
    - 可以优先使用哪些能力
    - 哪些能力过时

### Agent 感知物理时间

让Aagent能感知时间，知晓任务的异常状态，紧迫度  
比如正常就可100ms返回，结果超过了60s, 返回ok(可能就是不正常)

## 上下文压缩策略

### 本质

- 解决长度约束和成本约束
- 提升思考质量——总结后的知识比原始形式更利于模型使用

### 压缩方案

- 工具结果预算控制
- 噪声直接删除
- API 层微压缩 直接剔除工具的result
- 归档式摘要
- 全量压缩

### 压缩策略的设计原则

- 信息价值的非均匀分布 网页中的主信息，高于header和footer
- 语义完整性 （xxx时间xx人干了xx事）
- 任务相关性 压缩时保留什么信息，不是由信息本身决定的，而是由当前要完成的任务决定的
- 压缩即理解 压缩后的内容，能让人一眼看懂是之前做什么

### 隔离优于压缩：子 Agent 上下文隔离

压缩是在信息已经进入上下文之后做减法，而一个更釜底抽薪的思路是：让大体积的中间信息根本不进入主上下文

**用户记忆（个体尺度）**  
· 记忆层次 · 三层次评估

· 结构化索引：RAPTOR · GraphRAG  
· 文件系统范式 · 智能体化 RAG

**共享底层：检索技术**

## 用户记忆

存储格式 -> 怎么存  
记忆层次 -> 存在哪里  
认知类型 -> 存什么

### 用户记忆能力归类

个人信息保留：记住用户身份等长期个人信息  
偏好追踪：跟踪并记住用户的长期偏好  
上下文切换：在多个话题之间切换时保持连贯  
记忆更新：当用户提供与旧信息矛盾的新信息时能正确处理  
多会话连续性：跨会话保持知识  
复杂思考：基于多个记忆片段联合思考，例如当用户对花生过敏时推荐泰国菜应主动提醒注意花生成分  
时间感知：记住日期、理解相对时间、进行时间计算  
冲突解决：识别并处理记忆之间的不一致

### 记忆的三层次评估框架，拿到记忆可以做什么

第一层：基础回忆 够准确存储和检索用户直接提供的、结构化的、无歧义的信息
第二层：多会话检索 在多个回话检索相关的信息
第三层：主动服务 跨回话，通过记忆主动发起服务

### 存储格式

简单记录：用户的邮箱是xxx@mail.com
连续继续：用户在小学工作，是数学老师，班主任管理40名学生
JSON结构化事实：｛姓名，出生年月，电子邮箱｝
复杂JSON结构化事实 ｛背景，信息，关联｝

### 记忆层次

短期记忆：会话
长期记忆：跨会话
业务状态：执行的任务状态

### 认知类型

情景记忆（具体事件）
语义记忆（一般知识）
程序记忆（行为流程）

### 框架

mem0

### 记忆的评估与更新

多维打分检索：记忆按重要度 / 时间 / 相关性等多维打分，检索时综合排序召回高置信记忆。  
过期遗忘（Forgetting）：按时间 / 重要度淘汰过期或低价值记忆，防止记忆库无限膨胀。  
压缩摘要：把长历史记忆压缩成摘要存储，控制存储与检索成本。  
经验沉淀：任务结束后把「哪些做法有效」提炼成经验存为长期记忆，跨任务复用。

## RAG

检索相关片段 → 注入上下文 → LLM 基于上下文生成答案

### 文档分块三中方向

- 固定大小切分： 是每块 256-1024 token、相邻块重叠 10%-20%，根据检索质量实测调优
- 递归/结构感知切分 ：按文档的自然边界（章节标题、段落、句子）递归切分——先尝试按大边界切，块仍超长
  时再降级到更小的边界
- 语义切分：计算相邻句子的嵌入相似度，在语义“断崖”处（相似度骤降的位置）下刀，使每个块内部主题尽量
  单一。

### 稠密嵌入

计算机只能处理数字，不能直接理解“苹果”和“橙子”的含义。嵌入的思路是：把每
个词或句子转化成一串数字（称为“向量”，比如 [0.2, -0.5, 0.8, ⋯]）
把文本映射到向量空间，语义相近的内容，向量距离也近

### 稀疏嵌入

精确匹配的关键词检索
BM25算法，通过相似性进行打分

### 混合检索

稠密检索懂语义但可能漏掉关键词，稀疏嵌入则相反
同时进行极大改善召回效率(需要rerank介入)

### 智能rag

将rag作为工具交给agent自主执行，而不是把用户的输入进行rag召回后组织成上下文进行回答

### 知识的组织与检索
RAPTOR 和 GraphRAG

### RAPTOR
适用于文档
树形结构+文档摘要+文档聚类  
Chunk → 聚类 → 摘要 → 再聚类 → 再摘要
```

                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
       第一部分       第二部分       第三部分
          │            │            │
     ┌────┴────┐   ┌───┴────┐   ┌───┴────┐
     ▼         ▼   ▼        ▼   ▼        ▼
   第一章     第二章 第三章   第四章 第五章   第六章
```

# 评测和纠正
## 评测 
**一个流畅、详尽、礼貌的回答如果包含虚假事实，对用户的伤害远大于一个简短但准确的回答。**

### 五大核心指标
任务成功率：评测集里「完整达成用户意图」的占比——最核心指标。  
工具调用准确率：该调的调了 + 不该调的没调（闲聊触发检索也算错——过度调用浪费 token 且拖慢响应）。  
步骤数量 / token 成本：完成任务用了几轮循环、烧了多少 token；同等成功率下步骤越少越优秀——无限循环的 Agent 就是被这个指标暴露的。  
幻觉率：回答中「编造事实」的比例，靠 LLM 裁判 + 人工抽检结合评估。  
平均完成耗时：延迟体感指标。  

### 纠正的三种方式
1，提示词告诉他执行流程，不要做什么
2 添加验证工具，让agent自己执行
3 执行结果通过自定义规则验证，比如参数校验
